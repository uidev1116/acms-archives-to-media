メリット

  • 順番が固定なので迷わない。ドライランを飛ばして実行することが構造的にできない。
  • 1 回きりの移行作業（多くのサイトはこれ）にぴったり。
  • 画面の状態がジョブの状態とそのまま対応するので、実装とテストが素直。
  • 完了画面にテンプレートのヒントを出す流れが自然。

デメリット

  • 「このエントリーだけ先に変換して試す」といった寄り道がしにくい（除外はできるが、指名はしにくい）。
  • 過去のジョブの詳細を見る導線が弱い。
  • 設定画面が縦に長くなりやすい。
向いているケース: 一度で全部移行したい／作業者が CMS に詳しくない／まずはこれで十分、という場合。

メリット

  • 範囲を分けて何回かに分けて移行できる（「まず news カテゴリーだけ」など）。
  • 一時停止・再開・ロールバックの状態が一覧でわかる。チームで作業するときに安心。
  • データ設計（a2m_job / a2m_item）がそのまま画面になるので、拡張しやすい（例: 本文 HTML 置換のジョブ種別を追加）。

デメリット

  • 初めて開いた人には「まず何をすればいいか」が伝わりにくい。
  • 画面数が多く、実装・テストの量が A の 1.5 倍ほどになる。
  • 範囲が重なるジョブを作れてしまうので、ロックと重複チェックの説明が必要になる。
向いているケース: 大規模サイトで段階的に移行したい／複数人で作業する／将来ほかの変換ジョブも同じ画面に載せたい場合。

メリット

  • 「何が残っているか」が常に見える。移行の残量管理にそのまま使える。
  • 特定のエントリーだけ試す、問題のある行だけ外す、といった細かい操作が得意。
  • Dataview（行選択・絞り込み・列設定）の機能をそのまま活かせ、メディア管理画面と操作感が揃う。

デメリット

  • 数千件を一度に、という使い方では「全件選択」の導線が必要で、結局 A と同じ処理が要る。
  • 一覧を表示するために常に最新のスキャンが必要。大規模サイトでは画面を開くのが重い（スキャン結果のキャッシュ設計が必須）。
  • 「ジョブ」の概念が表に出ないので、ロールバックの単位がわかりにくい（操作ごとのジョブを裏で作ることになる）。
向いているケース: 中小規模のサイトで、内容を見ながら少しずつ移したい／テンプレートの改修と並行して、ページ単位で順に切り替えたい場合。

パターン比較

処理の中身（スキャン・チャンク実行・ロールバック）はどのパターンでも同じで、違うのは画面の構成だけです。あとから別パターンに作り替えても、バックエンドはそのまま使えます。

参考（作者の所感）: 「1 回で全部移す」が主な使い方なら A が一番安全です。A の完了画面にある「過去の実行」から B のジョブ詳細画面へ入れるようにすると、運用で困る場面（再開・ロールバック）も B の作り込み無しで十分カバーできます。決め手にしたいのは「一部だけ指名して試したいか」で、したいなら C の行選択を A のステップ 3 に取り込む形が現実的です。
